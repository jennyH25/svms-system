# Explanation ML

## Short answer

Yes, there is predictive analytics logic in the system.

However, this is not a full machine learning pipeline (no model training workflow, no saved model artifacts, no TensorFlow/PyTorch/scikit-learn stack). The project uses a lightweight statistical forecasting approach implemented directly in backend code.

## What is machine-learning related in this system

### 1) Student Analytics Forecasting (backend)

Location: server/index.js

The system computes a next-term violation forecast using a hybrid formula in these functions:

- calculateLinearRegressionNextY(points)
- calculateForecastCount(termSeries, nextSemester)

How it works:

1. Historical term totals are built (total violations per term).
2. A linear regression estimate is computed from historical points.
3. A recency estimate is computed using weighted recent terms (last up to 3 terms).
4. A seasonal estimate is computed from the same semester in previous school years (if available).
5. These estimates are blended with adaptive weights depending on data volume.
6. The final forecast is clamped to safe lower and upper bounds to avoid unrealistic spikes or negatives.
7. The result is rounded to an integer predicted violation count.

Important note for documentation:

- This is best described as a rule-based statistical forecasting model or heuristic predictive analytics.
- It is not a trained ML model with feature engineering, training-validation split, hyperparameter tuning, or continuous retraining.

## Dashboard Trends (what was used)

### 2) Violation Trends Over the Semester (descriptive analytics)

Locations:

- server/index.js (buildAnalyticsFromRecords)
- src/pages/admin/Dashboard.jsx

How it is computed:

1. Records are grouped by semester and month.
2. Counts per month are aggregated for each semester (1st Sem, 2nd Sem, Summer).
3. Data is sorted by month order and returned as trendBySemester.
4. The dashboard renders this as an interactive line/area trend chart with start/peak/latest summaries.

What this means:

- This part is descriptive analytics and visualization.
- It shows historical patterns/trends only.
- It does not run forecasting inside the Dashboard trend chart itself.

## Student Analytics Forecasting (what was used)

### 3) Forecast card and graph in Student Violation page

Locations:

- server/index.js (studentAnalytics payload from buildAnalyticsFromRecords)
- src/pages/admin/StudentViolation.jsx
- src/components/ui/AnalyticsLineGraph.jsx

Returned analytics payload includes:

- historyCounts (historical term totals)
- predictedNextTerm (next term label and predicted violations)
- predictedChangePercent (percent change vs current term)
- graphData

How UI uses it:

1. StudentViolation page requests /api/violation-analytics.
2. It builds graph data from historyCounts plus predictedNextTerm.predictedViolations.
3. It displays:

- A line graph (historical + forecasted next point)
- Predicted change percentage
- Forecast outlook card (projected next-term violations and target term label)

Interpretation for the paper:

- The graph is predictive analytics assisted by a backend statistical forecast.
- The predicted point is not generated by a deep learning model; it is generated by weighted regression + recency + seasonality logic.

## Data source behavior (important for methodology section)

Endpoint: GET /api/violation-analytics
Location: server/index.js

The analytics engine selects data depending on the target term:

- If requested term is the current ongoing term: reads current records from student_violation_logs.
- Otherwise: reads archived records from student_violation_archives, with workbook fallback/merge for historical entries.

Then it computes:

- Risk card metrics (active, warning, at-risk, high-risk)
- Trend-by-semester monthly counts
- Student analytics forecast outputs

This is useful to document because it explains why historical and current analytics can come from different storage sources.

## What is NOT present (to avoid overclaiming in the paper)

Not found in the codebase:

- No neural network or deep learning framework
- No external ML model service
- No model training scripts or serialized model files
- No online learning/retraining pipeline

So, the safest academic wording is:

- The system uses statistical forecasting and predictive analytics techniques, including linear regression and weighted trend blending, to estimate next-term violations.

## Suggested wording for your documentation paper

You can use this statement:

The system implements predictive analytics for student violation forecasting using a hybrid statistical approach. Historical term-level violation counts are processed through linear regression, recency-weighted averaging, and semester seasonality weighting to estimate the next-term violation volume. In parallel, the Dashboard Trends module provides descriptive monthly trend analytics per semester for monitoring historical behavior. This design enables actionable early-warning insights without requiring a full machine learning training pipeline.
